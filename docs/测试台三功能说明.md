# 测试台前三个功能：它们到底在干什么

> 2026-09-10。写给不想看代码的人。三个功能互相独立，可以只开一个。
> 一句话区分：**声音响应** = 听电脑在放的声音；**游戏伴随** = 看你在玩哪个游戏；
> **游戏桥** = 让游戏自己直接控制设备。

---

## 🎵 声音响应（两种模式：角色声音 / 音乐律动）

**它解决的问题**：让设备跟着你**电脑正在播放的声音**动——看片、听歌时机器跟着起伏。

- **它听的是什么**：耳机/音箱里正在**放出来的声音**（系统输出）。**不是麦克风**。
- **先选「响应对象」**（这是顶层二选一，它决定"设备到底在回应谁"）：

| 模式 | 听什么 | 怎么动 |
|---|---|---|
| **角色声音 · 呻吟 / 喘息 / 说话** | 只认 **150–1200Hz 的人声频段**，而且要求**中频占主要能量**（背景音乐、爆炸、鼓点会被排除） | **抽插（进进出出）**：一次呻吟 = 一次动作，越响抽得越深、越急跟得越紧；安静时完全不动 |
| **音乐律动 · 跟着鼓点和低音** | 鼓点、低音、整段音乐的起伏 | 持续律动（下面「律动方式」再选 自然起伏 / 低音节奏 / 鼓点脉冲） |

**「角色声音」模式的细节**（用户要的语义是"呻吟机器就插入"）：

1. **深度** = 行程 × 舒适档 × 人声强度（越响越深，安静时为 0）；
2. **速度** = **数她自己的节奏** —— 统计最近约 2 秒人声包络起伏了几次（颤音/喘息频率），
   夹在 0.5–2.2 次/秒；数不出节奏时回落到「0.6 + 1.2 × 强度」；
3. **起音**：一声刚起 → 立刻**插到底一次**（不让情绪最高点滑过去）；
4. **余韵**：最后一声落下后再抽 1.5 秒、幅度线性递减，然后缓慢回中停住；
5. 该模式**忽略**「事件化动作」勾选（那是音乐口径）。

**两个模式靠什么分开**（不是靠文案约定，是信号层面的判据）：

- 人声频段 = 150Hz 高通 → 1200Hz 低通；
- 但**只看绝对能量不够**：一阶高通对 55Hz 低音只衰减约 9dB，鼓点谐波会漏进来。
  所以两者都乘上同一个**中频占比**系数（宽带与中频的差值：0–3dB 算全占，9dB 以上算没占）——
  实测：呻吟素材的人声电平 **0.99**、纯 55Hz 低音 **0.00**、只有呼吸声的房间底噪 **0 次人声事件**。
- 单元测试锁死了这三条（`tests/Hexa.CoreTests`：女声 7 次 / 男声 8 次人声事件、底噪 0 次、低频不推高电平）。

**其他**

- **什么时候用**：想要"声音大就动得猛、安静就停"，且不需要游戏支持任何插件。
- **依赖什么**：设备已连接且没急停；「声音来源」选的是**真的在出声**的那个设备。
- **为什么看起来"没反应"**：系统静音 / 音量太小 / 选错输出设备；设备没连上或急停；
  被「游戏伴随」「游戏桥」或**正在播放的脚本**接管——卡片下面那行小字会写清原因。
- **已知小脾气**：三档「灵敏度」的差别不大，要调"多容易触发"建议直接用「行程」和系统音量；
  它只认系统输出，外放音箱 + 同时插着耳机时，要确认「声音来源」选的是正在响的那个。
- **诚实说明**：带人声的音乐（唱歌）会同时满足"角色声音"的判据——能量层面无法把"唱歌"和"呻吟"分开。
  想要哪种反应，由你选哪个模式决定。

## 🎮 游戏伴随 = 游戏期间的「调度者」（2026-09 重做）

**它解决的问题**：让设备"看你在干什么"——绑定的游戏在前台时才动，切出去（看视频、看网页）自动停住并缓降回中。
动作是即兴的、不重复的，不用你为每个游戏准备脚本。

### 先说清它的定位（这是重做的核心）

它**不是一个动作生成器，而是游戏期间的调度者**，只做三件事：

1. **判断该不该动**（绑定的游戏在前台？急停了吗？被桥接占用了吗）；
2. **给一个不重复的底色**（默认「自由巡游 · 自动换动作」，强度随场面缓慢起伏）；
3. **把反应权交给本来就更强的能力**：声音事件（冲击 / 渐强 / 节拍 / 呻吟）、你的操作（手柄活跃度、动作键）、游戏遥测。

> **为什么重做**：老版本是**靠"把别人都关掉"来独占设备的** —— 一开伴随，
> 声音响应的事件化引擎停摆、手柄活跃度进不来（`ApplyGamepadActivity` 挡一次、
> `EffectiveIntensity` 又丢一次）、快捷键脚本被**直接拒绝**，然后自己循环一个固定动作。
> 用户的原话是"如果没有什么特殊的，还不如用快捷键播放脚本来控制机器"——他说的没错：
> 那不是功能，那是一块独占的地皮，而且占下来之后放的是三样里最差的那一样。
> 现在这四处排他全部改成**让位**。

### 怎么用

1. 「目标游戏」填进程名（不知道就点「⏱ 3 秒后抓取」，切到游戏等 3 秒再回来）；
2. 选「动作来源」：
   - **自动**（推荐）= 有游戏信号（装了桥接插件）就跟着游戏，没有就用声音 + 你的操作兜底；
   - **只用声音** = 不理会游戏信号；
   - **只用遥测** = 收不到游戏数据就完全不动（装了插件的游戏选它，避免被环境声音误触发）；
3. 点「开启游戏伴随」。

### 开启后会发生什么

1. 绑定的游戏在前台 → 设备按**底色动作**即兴地动（默认自由巡游，会自己换动作，不重复）；
2. 听到**冲击**（枪声/爆炸/撞击）→ 切到抽插往复，强度按这一下的力度抬升；
3. 听到**渐强**（音乐起伏）→ 换自然流动；听到**节拍** → 一下一下的脉冲；
4. 听到**呻吟/人声** → 抽插（用户明确要的语义："呻吟机器就插入"）；
5. 你在激烈操作（手柄摇杆/扳机、动作键）→ 强度跟着抬起来（**伴随接管时这条不再被顶掉**）；
6. 事件过去 → 平滑回到底色（不硬切、不重启）；
7. **切出游戏 → 停住并缓降回中**（设计如此，不是坏了）。

### 它和你手动操作的关系（优先级）

`快捷键脚本 > 游戏桥 > 遥测 > 伴随`

- 你按快捷键放脚本 → 伴随**立刻让位**（不再拒绝播放），脚本停下/放完后如果游戏还在前台**自动接手**；
  - 细节：**暂停（⏸）也算脚本在场**，伴随会一直让位到你按停止或放完 —— 你按暂停就是想让它停住，
    这时让伴随接回去中位底色是反直觉的。让位期间你手动点「开启游戏伴随」也不会抢回设备；
  - 只有在**伴随仍开着 + 设备可动 + 已绑进程**这三个条件都成立时才会自动接手；
    伴随被关掉、设备掉线或急停锁定、没绑进程，都会保持停止。
- 游戏桥连着 → 桥说了算；
- 伴随是"默认背景"，任何显式操作都能盖过它。

### 为什么看起来"没反应"

进程名写错 / 目标游戏不在前台 / 设备没连接或急停 / 选了「只用遥测」但游戏没发数据。
卡片状态板会逐条写清：第 1 行是绑定与前台，第 2 行是**动作实际来源**（遥测·精确 / 声音兜底 / 等待遥测），
第 3 行是**正在响应什么**（冲击(0.62) / 你的操作 / 游戏遥测 / 只是底色 / 刚好在放脚本）或"现在不动：原因"。

### 最容易误解的两点

1. 它**不是**"开着就一直动"：不满足条件时它是停住的；
2. 它**不是**"动作是 Hexa 编的，跟游戏无关"：装了桥接插件时会完全跟随游戏数据，
   没装时才是"按声音和你的操作即兴"。

## 🖥 画面信号（观察模式，2026-09 新增）

**它是干什么的**：用户的主场景是"**跟着画面里的内容动**"（情色画面 → 设备动）。
声音只能到"有一下冲击"这一层，分不清画面里到底在发生什么，所以需要**看画面**。
这一步先做**只测量、绝不动设备**的观察模式：用真实内容验证信号够不够用，再决定要不要接进动作。

**怎么用**：测试台 → 「🖥 画面信号（观察模式）」→ 下拉选窗口（游戏或播放器都行）→ 点「开启观察」→
播放你的内容，看这四条数值和判定灯。用「灵敏度」滑块调判定线（界面会显示当前判定线的数值）。

**它算了什么**（全部在本机、只保留一块 160×90 的小缓冲）：

| 数值 | 含义 | 怎么算 |
|---|---|---|
| 肤色占比（整幅 / 中央） | 画面里有多少"像皮肤"的像素 | RGB 五条件 + YCbCr 区间**两条都中**才算（保守，宁可漏报）；另外单独算中心 60% 区域 |
| 中央运动量 | 画面中央动得多不多 | 相邻帧平均亮度差 |
| 节奏性 | 有没有 **0.5–3Hz 的周期性**推拉/晃动 | 3.2 秒窗口去线性趋势后做自相关，只取带内**局部极大** |
| 呻吟事件 | 刚才有没有呻吟/人声 | 直接读音频那边的人声事件（不重做分析） |
| **场景强度** | 融合分（0–1） | `中央肤色 × (0.5 + 0.5×节奏) × (呻吟时 ×1.25)`，带迟滞（进 0.38 / 出 0.26 @ 灵敏度 1.0） |

> 节奏那一步是**刻意的**：只取"带内峰值"的写法会把**缓慢漂移**误判成 0.92（比真节奏还高），
> 加上"局部极大"判定后：缓慢漂移 **0.00**、1.5Hz 推拉 **0.65**、2Hz **0.75**、纯噪声 0.21。

**隐私与边界（写进代码，不是口头保证）**：
- **不写盘、不保存截图、不生成缩略图、不上传**；只复用同一块小图缓冲；
- **默认关闭**；只抓你选的那个窗口（服务主动过滤掉自己进程的窗口）；
- 采样约 13 帧/秒：**超过 6.5Hz 的运动会被混叠**，别当频谱仪用；
- 独占全屏抓不到 → 状态行会直接说「改成无边框窗口再试」，并自动退化为按窗口矩形从屏幕抓；
- 已用自检锁死：**观察模式一条 TCode 指令都不发**（1.5 秒内新增 0 条）。

**验证通过后**（第二步，尚未实现）：它会成为**游戏伴随的「动作来源」第四个选项（画面内容）**——
场景强度决定抽插的深度与速度，呻吟事件仍然当"起音"。名称与归属都属于**游戏伴随**，与「声音响应」无关
（声音响应只管纯音频场景：看片/听歌，不看屏幕）。

## 🌉 游戏桥 + 🔍 指令监视

**它解决的问题**：让**支持 Intiface / Buttplug 协议的游戏**把动作直接发给 Hexa，Hexa 翻译成设备指令——
不需要游戏专门适配 Hexa。

- **怎么用**：点「开启游戏桥」→ 在**游戏自己的设置里**把设备地址填成 `ws://127.0.0.1:<监听端口>` →
  游戏扫描到「Hexa OSR6」设备后，游戏里的动作就由它控制。
- **开启后会发生什么（逐步）**：
  1. 开启瞬间 Hexa 自己的动作先停（避免两路指令打架）；
  2. 游戏连上（状态行出现客户端数）→ 游戏全权控制设备；
  3. **游戏断开 / 退出 → 设备自动回中**（注意这是一次你没主动要求的动作）；
  4. 点「关闭游戏桥」或急停 → 立刻断流。
- **两个下拉的意思**：「呈现模式」= 告诉游戏"你有几台设备"（单桥 = 1 台既能直线又能旋转；双桥 = 2 台）；
  「振动响应」= 万一游戏发振动指令怎么办（本机没有振动配件，保持「关闭 / 忽略」即可）。
- **「延迟补偿」**：画面比设备慢就把值调大，反之调小；0 = 不补偿。
- **指令监视是什么**：RX = 游戏发来的原始指令，TX = Hexa 真正发给设备的指令。
  **设备没反应时就盯这里**：只有 RX 没有 TX = 指令没翻译出去；TX 后面跟着「⚠ 输出已锁定」= 设备没连上或处于急停。
- **为什么看起来"没反应"**：游戏根本没连上（客户端一直是 0）；端口被占用；同时开着声音响应 / 游戏伴随（会抢设备，
  现在游戏桥优先，声音响应会主动让位并写明原因）。

## 三者同时开时的优先级（本轮明确的规则）

1. **急停** 最高：任何时候都能立刻停住一切。
2. **手动播放的脚本**（快捷键 / 脚本库点播放）：显式操作优先，**伴随与声音响应都让位**，播完自动交还。
3. **游戏桥**：只要游戏连着，就由游戏控制设备；**声音响应会主动让位**（卡片上会写「游戏桥正在控制设备」）。
4. **游戏遥测**：绑定的游戏在发数据时，按游戏数据驱动。
5. **游戏伴随（底色 + 事件反应）**：目标游戏在前台时接管。
6. **声音响应**：以上都没在控制时才驱动设备。

本轮同时补上的两点安全限制：游戏桥下发的动作现在会**夹进你设置的轴限位**，并且**最小插值 60ms**
（游戏发「1 毫秒走完全程」也不会再原样执行）。

## 沉浸感相关的两个新开关（2026-09-10 加）

三个功能都"看不见游戏里发生了什么"，所以它们能给的是**氛围沉浸**，不是"动作和画面对上"的沉浸。
在这个前提下，能明显提升沉浸感的是这两条：

### 1. 「安静时停住」（默认开）
游戏伴随启动的动作，现在会看**电脑有没有在放声音**：

- 没声音持续 0.7 秒 → 缓慢回到中位并**停发指令**（设备静止）；
- 声音回来 → 自动继续动，声音越大动作越强。

理由：一直轻微动是背景噪音，**静止本身才更沉浸**——平时安静、有事才动。
自己到「游玩」页按的「开始自动」**不受这个开关影响**（你按了就该一直动）。

### 2. 每个游戏一套配置
在「游戏伴随」卡片上可以点「记住当前设置给这个游戏」：把这个游戏的动作风格和强度单独存下来，
下次进这个游戏自动用它，不用重新调。没存的游戏继续用全局的「底色动作 / 强度」。
（**两条路径都吃这份配置**：不管走规则路径还是"伴随关闭时的自动套用"，读的都是同一套，见 `GameCompanionRules.Apply` 与 `ForegroundWatcher`。）
想删掉就点「删除该游戏配置」。
（存储位置：`settings.json` 的 `GameProfiles`，键是游戏进程名。）

### 三个功能在沉浸感上的真实定位

| 功能 | 能提供什么 | 上限在哪 |
|---|---|---|
| 🎵 声音响应 | **氛围**：跟着内容的时间曲线起伏（或按人声抽插） | 只跟声音，不知道游戏状态 |
| 🎮 游戏伴随 | **存在感 + 即兴**：进游戏就有动作、不重复，并且**转发放大**声音事件（冲击/渐强/节拍/呻吟）与你的操作 | 没有插件时它不知道你赢了还是死了，只知道"在玩、有多激烈" |
| 📜 快捷键脚本 | **精确的桥段**：想放就放，伴随自动让位、播完交还 | 需要先有脚本；同一段会重复 |
| 🌉 游戏桥 | **真正的同步**：动作由游戏事件决定 | 依赖游戏支持 Intiface；很多游戏只给一根轴 |
| 📜 funscript | **真正的同步**：逐帧对好时间 | 需要先有脚本（自己画或下载） |

一句话：**想要"和画面对得上"的沉浸，只有游戏桥或 funscript 能做到；前面三个是"没有它们时"的氛围替代品。**

## 沉浸感改造（2026-09-10 第二批）

前面说过："三个盲功能的上限是氛围，不是沉浸。"这一批就是**在它们的能力范围内把沉浸感做到头**——
核心思路一句话：**动作要由"刚发生的事"触发，而不是由时钟触发。**

### 1. 事件化动作（声音响应默认走这条）
不再"跟着音量一直循环"，而是从声音里**识别事件**：

| 事件 | 什么情况 | 动作长什么样 |
|---|---|---|
| **冲击** | 爆炸、枪声、撞击（瞬间变响） | 快而深，打完就回落，带一点扭转 |
| **渐强** | 音乐起伏、引擎轰鸣（慢慢变响） | 慢而连贯的一个完整来回 |
| **节拍** | 有节奏的重复点 | 短、轻、跟拍 |

**没有事件时设备是静止的**——静止本身才是沉浸感（一直轻微动 = 背景噪音）。
实测：一段"每秒一次冲击"的音频，6 秒内准确识别 6 次事件，类型判定为"冲击"。

想回到老的"跟着音量循环"行为，把「事件化动作」关掉即可（关掉后行为与以前完全一致）。

### 2. 多轴动作语汇
六轴不再只用一根：冲击加一点扭转（R0/R1）、慢段落加倾斜（L2/R2）、渐强加次要推进（L1）。
只用一个轴，机器就只是"会动的棒子"；多轴协调才有"这台机器在回应画面"的感觉。
关掉「多轴动作语汇」后，除 L0 外的轴一律保持中位 50（实测确认）。

### 3. 无缝切换与优雅停止
- **离开游戏不再"急停"**：改成 0.6 秒缓降回中后停发（急停按钮仍然是立即停）。
- **进入游戏 / 切规则不再"停一下再起"**：新模式的第一帧如果离当前姿态很远，会用 300ms 长插值滑过去，
  并且软启动包络从**当前位置**起步，而不是从零开始。
- **规则小改不重启**：同一动作族、强度差 < 0.2 时只改参数（靠引擎的强度 ramp 交叉淡入），不 StopAll。

### 4. 对齐校准（±200ms）
画面/声音和设备对不齐是最常见的"感觉不对"。声音响应卡片下可以调一个偏移量（正 = 设备晚一点动），
配合「▶ 测试对齐」的 1Hz 测试（界面闪烁 + 设备同步动一下），拖到看着对齐为止。

### 边界（说清楚免得期待落空）
这些改造提升的是**同一个功能内部的质感**：时机更准、动作有起落、切换不打断。
但"动作与画面事件一一对应"这件事，前面三个盲功能**依然做不到**——
那需要**游戏桥**（游戏自己发动作）或 **funscript**（逐帧对好时间）。
