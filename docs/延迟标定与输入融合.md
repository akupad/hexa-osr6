# 延迟标定（③）与输入融合（⑨）

## 一、延迟标定：先把"能算的那一半"算出来

沉浸感最容易被破坏的地方是**动作和画面差半拍**。这个延迟由两段组成，只有第一段能自动测：

| 段 | 是什么 | 能不能自动测 |
|---|---|---|
| **设备侧** | 从发出指令到设备走到位：受舒适档的速度/加速度/加加速度上限约束 | ✅ 能。用**真正的安全限速器**把这段行程跑一遍即可 |
| **画面侧** | 游戏渲染 + 显示器 + VR 合成 | ❌ 不能。Hexa 看不到画面，只能由用户看着调 |

**入口**：测试台 → 声音响应卡 → 对齐校准 → **「⏱ 测设备到位时间」**

点一下会：用当前舒适档模拟设备走 60 个行程点（从 20 到 80），显示耗时，并把「对齐偏移」自动设为
`−耗时/2`（设备到位比事件晚，所以让它提前一点发出；感知到的动作大致在行程中段）。
画面侧剩下的部分，仍然用旁边的滑块看着对齐微调。

**实现要点**（`Services/LatencyCalibrator.cs`）：

- 用 `MotionSafetyLimiter` **真跑一遍**，不是解析公式。原因：解析的梯形曲线只是物理下限
  （实测沉浸档 60 个点只有 ~317ms），而限速器实际是逐帧追击式控制（带停止距离与加加速度限制），
  实测 816ms——差 2.6 倍。拿解析值当标定结果会差得离谱。
- 量到**走完 90% 行程**为止，而不是"完全停在目标上"。原因：限速器在目标附近本身会有余摆
  （既有特性），量到完全停下来会把余摆的尾巴算进去，结果**反而随速度上限升高而变长**（越快越摆），
  完全不能反映手感上的滞后。90% 那一刻才是玩家感知到的"到位"。
- 单测保证：估算值和"手工用限速器跑一遍"逐轴一致（误差 ≤1 帧），且随舒适档变慢而变长、随次要轴系数变小而变长。

## 二、输入融合：从"互相抢占"到"分层"

原先所有来源（脚本 / 遥测 / 游戏桥 / 手柄 / 声音 / 自动）是**互相抢占**的：谁抢到谁动，另一个就得让位。
现在分成三层：

| 层 | 谁在里面 | 规则 |
|---|---|---|
| **主运动层** | 桥 > 遥测 > 脚本 > 伴随/自动 | 同一时刻只有一个主人（沿用原有的 claim 机制） |
| **氛围叠加层**（新） | 声音能量 / 事件语汇 | 可以在**精确动作之上叠加**，也可以关 |
| **整形与安全层** | 游戏桥整形、安全限速器、多轴门控 | 两层出来的动作都要过这里 |

**氛围叠加**（测试台 → 声音响应 → 「氛围微动叠加」，**默认关**，幅度 5–30% 默认 12%）：

- 只走**次要轴**（L1/L2/R0/R1/R2），各轴相位错开，2.6 秒一个来回的慢摆（像呼吸，不像抖）；
- **主轴 L0 一个字节都不动**——它归游戏/脚本的精确意图；
- 只认"新鲜的"音频特征（采集停了就不叠），安静时（能量 ≤0.05）也不叠；
- 幅度按音量缩放，且叠加结果照样过**多轴门控 + 安全限速器**，限位/速度/加速度上限一个都突破不了。

**实测（单元测试）**：次要轴偏离中位的均方根，关叠加时 0.00 → 开叠加 17.51 → 声音停了 8.32（显著回落）
→ 关掉「多轴动作」总开关后 0.00（门控说了算，氛围层顶不开）。主轴位置在所有情况下都保持在被要求的值上。

> 注：那 8.32 的残差是**安全限速器自身的余摆**（既有特性，不是叠加层没关）：目标回到中位后它还会在附近摆一会儿。
> 这也说明"限速器在目标附近的收敛"是这个项目里反复出现的一个可改进点，值得单独一轮。
