## 动作整形：游戏指令 → 连续、立体的动作（新增，默认开两条）

游戏桥原来是**原样透传**：游戏发什么就拼成 TCode 发给设备，只有两道安全阀（轴限位夹紧、
插值时间不小于 60ms）。问题是游戏指令的形态和脚本完全不同——**每 20–50ms 一条、常常只驱动一根轴、
强度还带噪声**（帧率抖动、mod 算法抖动），原样透传的结果就是"抖 + 平"。

现在桥的 50ms 节拍上跑一条整形管线（和延迟补偿同一个节拍）：

| 开关 | 默认 | 作用 |
|---|---|---|
| 指令平滑（去抖） | **开** | 一阶低通按固定节拍追目标，而不是一条一条原样转发；平滑时间 0–300ms 可调（越长越柔、越滞后） |
| 多轴联动 | 关 | 游戏只驱动 L0 时，按和脚本播放相同的规则带起其它轴（快的地方加扭转、上下带左右倾）；正在旋转的轴不会被抢 |
| 也遵守「舒适档」限速 | **开** | 每个节拍最多走「舒适档速度上限 × dt」。旧行为只有 60ms 插值下限（≈1667/秒），比沉浸档 360/秒 快四倍多 |

**三个都关 = 完全回到旧行为（原样透传）**，所以随时可以退回去对比。

实测（单元测试 + 服务级冒烟）：

- 同一条「1.0 全行程 / 200ms」指令：整形关 → 串口出现 `L09999I200`（一步到底）；
  整形开 → 按节拍分三步以上爬升，插值时间用 60ms（设备不会被一次跳满行程）。
- 抖动抑制：目标在 40/60 之间来回跳时，整形后的输出摆幅不到原来的 60%。

整形只改"动作怎么落地"，不改游戏的"什么时候发什么"：急停、轴限位、让位逻辑、断线归中一个没动。

## 指令监视读法

- **RX** = 游戏发来的原始指令（Intiface / Buttplug 协议侧）。
- **TX** = Hexa 实际发给设备的 TCode。
- 两者对照可定位「游戏发了但设备没动」的链路问题；「自测」用于在不启动游戏的情况下验证
  「映射 → 串口 → 设备」整条链路。

## 振动响应：OSR6 没有振动附件，这一项只决定「万一收到 VibrateCmd」怎么办

先说清楚前提：**OSR6 六轴本体没有振动附件**（V0/V1/A0/A1 都未安装），而且
`IntifaceBridgeService.DeviceListJson()` / `DeviceAddedJson()` 向游戏宣告的设备能力里
**只有 `LinearCmd` / `RotateCmd` / `StopDeviceCmd`，不包含 `VibrateCmd`**——
所以正常游戏根本不会发振动指令。

「振动响应」下拉（`BridgeVibrateModeCombo`，`Views/TestLabPage.xaml` 的 `ToolTip` 也写了同一段话）
的两项语义因此只是兜底：

- **关闭 · 忽略振动指令（推荐）**（`off`，默认）：协议层 `IntifaceProtocol.Process()`
  仍回 `Ok`（避免游戏判定设备掉线），但**不下发任何动作、也不计入 TX**。
- **透传 V0 · 本机无振动附件，无实际效果**（`position`）：万一收到 `VibrateCmd`，
  原样转发到振动通道 `V0`（`IntifaceBridgeService.VibrateAxisFor()` 恒返回 `"V0"`，
  `SetVibrateState()` 直接下发 `V0{强度}`），**不做任何轴映射**；本机固件会忽略 `V0`。

失效的「往复模拟」已删除；`AppSettings.GameBridgeVibrateMode` 归一化只接受 `position` / `off`。

## 声音响应：首次开启先确认，旁边新增「■ 停止」

`Views/TestLabPage.xaml.cs` 的 `AudioToggle_Click`：

- **首次开启会先弹确认**：「开启声音响应会立即开始自动动作（设备会动），是否继续？」
  （默认按钮 = 否）。原因是 `AudioReactiveService.StartCapture()` 在
  `AudioReactiveEnabled && !RuleEngineActive && !AutoRunning` 时会直接 `StartAuto()`。
- 选「否」会**回滚开关状态**（不写配置、不启动捕获，按钮文案与样式恢复成「开启声音响应」）。
- 按进程记忆：本次运行确认过一次后不再重复弹（`_audioEnableConfirmed`）。
- 卡片文案已改成诚实的说法：「开启后设备会立即开始自动动作；声音只改变强弱和节奏。」
- 旁边新增 **「■ 停止」** 按钮（`AudioStopBtn` → `AudioStopBtn_Click`），
  行为等同页面底部的一键停止（含急停与关闭自动跟随），提示里写明了这一点。

## 一键停止：「⛔ 全部停止并关闭自动跟随」

按钮 `StopBtn` 的文案已从「⛔ 全部停止」改为 **「⛔ 全部停止并关闭自动跟随」**
（`Views/TestLabPage.xaml`），因为它的实际作用远不止急停。`StopBtn_Click` 会：

1. 先取消勾选「自动跟随」`CompanionAutoCheck` 与「操作联动」`ActionLinkCheck`，
   并调 `SaveAutoFollow()` **落盘** `CompanionAuto=false` / `ActionLinkEnabled=false`；
2. 关掉游戏伴随（`RuleEngineEnabled=false`）、声音响应（`AudioReactiveEnabled=false`）、
   游戏桥（`GameBridgeEnabled=false`），`_rules.Stop()` / `_audio.Refresh()` / `App.Bridge.Refresh()`；
3. `App.Engine.EmergencyStop()` 锁定输出，`App.Settings.Save()` 落盘。

**为什么必须先关自动跟随**：否则用户解锁后切回目标游戏，`ForegroundWatcher.Tick` 看到
`CompanionAuto=true` 会再次 `StartAuto()`，设备重新运动。停止后状态栏
（`RefreshAutoFollowStatus()`）会显示 **「自动跟随已关闭 · 切回游戏不会再自动启动」**，
底部提示 `StopHintText` 也会说明「解锁后如需自动跟随，请重新勾选」。

## 监听端口校验

`ApplyBridgeSettings()`（由 `BridgeSetting_Changed` 或 `BridgePortBox_KeyDown` 触发）：

- 只有能 `int.TryParse` 成整数、且落在 **1024–65535** 范围内的值才会写入
  `App.Settings.GameBridgePort`；
- 非法值会被**拒绝并提示**「端口需为 1024-65535 的整数，已保留 {旧端口}。」
  （`BridgePortHint`，Danger 色），同时把输入框恢复成旧端口，不静默丢弃；
- `BridgePortBox_KeyDown` 里 **按 Enter 立即应用**（`e.Handled = true` + `ApplyBridgeSettings()`），
  不再只在失焦时生效。

## 指令日志：增量追加 + 只在底部时自动滚动

`RefreshBridgeLog()`（`Views/TestLabPage.xaml.cs`）本轮改动：

- 日志改为**增量追加**到 `ObservableCollection<BridgeLogLine>`（`_bridgeLogLines`），
  用 `_lastBridgeLogEntry` 定位上次追加到的条目，不再每次整表重建 + 逐行 `FindResource`；
  显示上限仍是 120 条，超出从头部移除。
- **只有当你已经在列表底部时才会自动滚动**：先 `IsBridgeLogAtBottom()` 记住用户位置
  （容差 4px），是底部才 `BridgeLogList.ScrollIntoView(_bridgeLogLines[^1])`；
  向上翻看历史时不会被弹回底部。
- 前台进程名改为 **1 秒缓存**（`ReadForegroundProcessNameCached()`）：150ms 的轮询不再每次都
  `Process.GetProcessById` 枚举前台进程；回到页面时会把缓存置为失效立即刷新一次。

## 「⏱ 3 秒后抓取」：读不到前台进程时保留原绑定
