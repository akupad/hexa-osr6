# 安全与数据保护（本轮修复清单）

> 状态：已落地（2026-09-09 晚）。本页只记录**本轮修掉的高风险项**，每条写清
> 「以前会怎样 → 现在怎样」，并注明是在哪个文件 / 方法里核实的。
> 这些改动的共同点：**不让任何自动路径悄悄解除急停、不让任何误触直接驱动设备、
> 不让任何失败路径静默丢数据**。

## 1. 鼠标滚轮扫过「轴限位」双滑块会改限位并立刻驱动设备

- **以前**：鼠标滚轮只要扫过设置页的限位 `RangeSlider` 就按 `SmallChange` 改值；
  由于拖动限位会实时下发，**一次无意的滚轮就能移动设备**。
- **现在**：滚轮**默认不再改值**——`RangeSlider.IsWheelAdjustEnabled` 默认 `false`，
  `OnCanvasMouseWheel` 直接返回且不标记 `Handled`，让滚轮冒泡给外层 `ScrollViewer` 正常滚动页面；
  并且**限位实时驱动需要显式勾选**「拖动限位时实时驱动设备」（默认关，选择会持久化）。
- **核实**：`Controls/RangeSlider.cs` 的 `IsWheelAdjustEnabled` / `OnCanvasMouseWheel`；
  `Views/SettingsPage.xaml.cs` 的 `BuildAxisLimitGrid`（`IsWheelAdjustEnabled = false`）、
  `LiveLimitDriveCheck.Checked/Unchecked`、`DriveAxisFromSlider`；
  `Models/AppSettings.cs` 的 `LimitSliderDriveDevice`（默认 `false`）。

## 2. 「全部归中」会静默解除急停并重新使能输出

- **以前**：`MotionEngine.Home()` 会 `EmergencyStopped = false` 并重新使能输出，
  侧栏常驻的「全部归中」按钮误触一下就把用户刚按下的急停解除了。
- **现在**：**三个入口都会先确认**——主窗口侧栏（`MainWindow.HomeBtn_Click`）、
  校准窗口（`CalibrationWindow.Home_Click`）、设置页（`SettingsPage.HomeBtn_Click`）；
  用户点「否」直接 return，不调 `Home()`。
- **核实**：`MainWindow.xaml.cs` 第 155–162 行、`Views/CalibrationWindow.xaml.cs` 第 82–90 行、
  `Views/SettingsPage.xaml.cs` 第 886–893 行；`Services/MotionEngine.cs` 的 `Home()`
  （第 286–297 行注释写明会解除急停并重新使能输出）。

## 3. 游戏桥断开自动归中会静默解除急停

- **以前**：游戏客户端断开后 `ResetToCenter()` 无条件 `_engine.Home()`，
  急停锁定中也会被自动解除，用户按下的急停被一条自动路径取消。
- **现在**：急停锁定中**不再自动归中**——只发 `DSTOP`，状态写
  「游戏断开 · 急停锁定中，未归中（点「全部归中」可解锁）」。
- **核实**：`Services/IntifaceBridgeService.cs` 的 `ResetToCenter()`（第 318–334 行）。

## 4. AI 说「归中 / idle」会静默解除急停

- **以前**：AI 助手执行 `idle` 场景会直接 `_engine.Home()`，等于替用户解除急停。
- **现在**：急停锁定中 **AI 拒绝执行**并提示「设备处于急停锁定，AI 不会自动解除急停。
  请到主界面点「全部归中」并确认。」
- **核实**：`Services/AiAssistantService.cs` 的 `SetScene`（第 486–499 行）。

## 5. presets.json 解析失败会静默覆盖用户全部自定义动作

- **以前**：`presets.json` 解析失败后回退内置动作，并把内置数组写回文件，
  用户辛苦调的动作库被整批覆盖。
- **现在**：解析失败**先改名备份**为 `presets.json.bad-yyyyMMddHHmmss`（同名冲突自动换后缀）
  并提示用户，本次使用内置动作；**只有文件根本不存在**（首次运行）才写出内置动作。
  备份本身失败时原文件保持不动、也不会再写盘覆盖它。
- **核实**：`ViewModels/StrokesViewModel.cs` 的预设加载路径（第 60–96 行）、
  `BackupBrokenPresetsFile`（第 101–120 行）、`ReportPresetsLoadFailure`（第 122–132 行）。

## 6. 动作编辑器关闭无未保存确认 / 保存失败污染内存

- **以前**：点「取消」或窗口 X 会静默丢掉刚调好的参数；保存写盘失败时，
  活对象已被改过，出现「界面按新参数跑、文件却没改」的不一致。
- **现在**：有未保存改动时关闭会先确认「有未保存的改动，确定放弃？」；
  保存改为**先写盘、再改活对象**，写盘失败就提示「写入 presets.json 失败……动作未保存」并 return，
  正在用的实例保持原样。覆盖内置动作前还会二次确认并留 `presets.json.bak`。
- **核实**：`Views/StrokeEditorWindow.xaml.cs` 的 `Closing` 守卫（第 96–105 行）、
  `_isDirty` / `MarkDirty`（第 47–110 行）、保存路径（第 771–810 行）、
  `BackupPresetsFile`（第 815 行附近）。

## 7. 退出程序不提示未保存的合成

- **以前**：托盘「退出」或真实关闭窗口直接退出，编排页里没保存的合成丢掉。
- **现在**：托盘「退出」和真实关闭都会确认（`ConfirmExitWithUnsavedWork`：
  先保存 / 直接退出 / 取消）；用户取消或保存失败时中止退出，窗口保持打开、托盘图标恢复。
- **核实**：`MainWindow.xaml.cs` 的 `OnClosing`（第 75–92 行）、`ForceClose`（第 98–107 行）；
  `App.xaml.cs` 托盘「退出」菜单（第 320–329 行）；
  `Views/EditorPage.xaml.cs` 的 `ConfirmExitWithUnsavedWork`（第 2531–2544 行）、`HasUnsavedWork`。

## 8. 手画波形（微调波形页）根本不落盘

- **以前**：手画波形只存在 `MotionEngine.EditWaves` 内存里，关掉程序就没了，
  只能靠「保存预设」手动导出，用户画完直接关窗口就全白画。
- **现在**：退出时自动存草稿 `%LOCALAPPDATA%\Hexa\wave-draft.json`，下次启动自动恢复并在
  波形页提示「已恢复上次退出时的手画波形草稿」；**退出时若六轴都空，草稿会被删除**
  （不会把已经不要的波形又恢复回来）；草稿文件损坏时删除并忽略。
- **核实**：`Services/WaveDraftStore.cs` 的 `Save` / `Clear` / `Load`；
  `App.xaml.cs` 的 `OnExit`（第 405–409 行）、`OnStartup`（第 94–101 行）；
  `Views/EditorPage.xaml.cs` 的 `ShowWaveDraftHintOnce`（第 2490–2496 行）。

## 9. 脚本库导入 / 重命名会静默覆盖同名脚本

- **以前**：导入或重命名时库内已有同名 `.funscript` 会被直接覆盖。
- **现在**：UI 层先算目标路径并**弹确认**「库内已有「X」，覆盖它？」；
  用户拒绝时绝不写盘。服务层 `ScriptLibrary.Import` / `Rename` 在 `overwrite=false`（默认）时
  遇到同名会抛 `InvalidOperationException("同名脚本已存在")`，从底层兜住静默覆盖。
- **核实**：`Views/ScriptLibraryPage.xaml.cs` 的 `Import_Click`（第 90–101 行）、
  `Rename_Click`（第 155–166 行）；`Services/ScriptLibrary.cs` 的 `Import`（第 64–78 行）、
  `Rename`（第 80–94 行）。

## 10. AI 助手「📦 角色卡」面板永远不可见

- **以前**：XAML 里给面板写了本地 `Visibility="Collapsed"`，本地值优先级高于 Style 触发器，
  导致展开用的 `IsImportOpen` DataTrigger **永远失效**，角色卡面板点不开。
- **现在**：默认收起改由 Style 的 `Setter` 负责，本地值删除，面板可正常展开。
- **核实**：`Views/AiAssistantPage.xaml` 第 110–121 行的注释与 Style（`DataTrigger IsImportOpen`）。

## 11. 「全部停止」不关自动跟随

- **以前**：一键停止只做急停与关功能，`CompanionAuto` 仍为 `true`；用户解锁后切回目标游戏，
  `ForegroundWatcher` 又会 `StartAuto()`，设备重新运动。
- **现在**：按钮改为「⛔ 全部停止并关闭自动跟随」，`StopBtn_Click` 先取消勾选并**落盘**
  自动跟随 / 操作联动，再急停；状态栏显示「自动跟随已关闭 · 切回游戏不会再自动启动」。
- **核实**：`Views/TestLabPage.xaml.cs` 的 `StopBtn_Click`（第 708–740 行）、
  `SaveAutoFollow`（第 313–328 行）、`RefreshAutoFollowStatus`（第 636–678 行）。
  详见 `docs/测试台-游戏桥与指令监视.md`。

## 12. 按钮文字对比度（绿底 / 红底上的浅色字）

- **以前**：`App.xaml` 的隐式 `TextBlock` 样式把 `Foreground` 钉死成 `Text` 色，
  它比按钮样式 Setter 的优先级更高，于是 `BtnPrimary` / `BtnDanger` 设的深色前景被盖掉，
  绿底 / 红底上出现对比度不足的浅色文字。
- **现在**：按钮模板在 `ContentPresenter.Resources` 里放了一个局部隐式 `TextBlock` 样式，
  把文字颜色绑回按钮自己的 `Foreground`——绿底 / 红底用深墨字
  （`OnPrimaryInk #04201A` / `OnDangerInk #2A0B0B`）。
- **核实**：`App.xaml` 的隐式 `TextBlock` 样式（第 40–41 行）、`BtnBase` 模板
  （第 482–495 行注释与 `ContentPresenter.Resources`）、`BtnPrimary` / `BtnDanger`（第 514–522 行）、
  `OnPrimaryInk` / `OnDangerInk`（第 27–30 行）。
- **实测对比度**（按 WCAG 相对亮度公式计算）：
  `OnPrimaryInk` 压 `Primary` = **6.76:1**；`OnDangerInk` 压 `Danger` = **4.95:1**。
  对照：白字压 `Primary` 只有 **2.53:1**、压 `Danger` 只有 **3.69:1**
  （与 `App.xaml` 第 27 行注释写的 2.5:1 / 3.7:1 一致）。
  > 注：任务书里写的是「约 7:1 / 5.5:1」，按上面公式实算为 6.76:1 / 4.95:1，
  > 取整/四舍五入口径不同会有偏差，以实算值为准。

## 两条刻意保留的差异（不是疏漏，是定下来的规则）

界面打磨那一轮，子代理各自独立工作，于是出现了两处"看起来不一致"的地方。
主代理逐条评估后**决定保留**，理由记在这里，避免以后被当成 bug 又改回去。

### 1. 「全部归中」的确认级别：侧栏不弹框、设置页弹框

- **规则**：凡是**会解除急停**的归中，一定先弹确认框；普通的归中不弹。
- 主窗口左下角「⬆ 全部归中」是专用按钮、位置固定、标签就是它要做的事，
  点它的人意图明确；而且它在急停后是最常用的"解锁"入口，每次都弹框是纯摩擦。
  （急停锁定态它仍然会先弹确认，因为那一步会重新使能输出。）
- 设置页「轴限位」卡里的「全部归中」夹在保存限位/重置/校准向导之间，
  误点概率高得多，所以那里**只要连着设备就一定先确认**。
- **核实**：`MainWindow.xaml.cs` 的 `HomeBtn_Click`（仅急停时确认）、
  `Views/SettingsPage.xaml.cs` 的归中处理（连着设备就确认）。

### 2. AI 助手控制设备：**条件式确认**（2026-09 已实现，取代原"完全不做确认"）

- 现状：AI 调工具是**调用即执行**，页面拿到的是**事后回执** —— 聊天区里会给一条
  「🎛 设备动作 · 场景换成 X · 速度 1.0→1.8」，顶部常驻一行
  「AI 会自己让设备动，按左侧急停或直接说停」。
- **原结论（"完全不做确认"）已作废**：2026 年的成熟做法不是"逐次弹框"，而是**按解析后的参数做条件判定**
  （OpenAI Agents SDK 的 `needs_approval` 谓词、MCP 的 `destructiveHint`）——只对真正有风险的动作拦一下。
- 现在的实现：`Services/AiAssistantService.cs` 里有一个**可取消的执行前事件**（`ConfirmToolAsync`），
  由界面用**非模态 3 秒倒计时条**实现（不占双手、可点「不要」取消，取消理由会回灌给模型）。
- **触发判据**（只看解析后的参数）：轴偏离中心/振幅 ≥ 40、速度 ≥ 2.5 档、hold/tease/nudge 时长 > 20 秒、
  **从静止启动运动**（当前没有任何驱动源在动而这次要开始动）、以及**参数畸形**（解析失败一律问，fail-closed）。
  `stop / pause / get_state` 这类安全动作**永不询问**。
- **fail-closed**：没有订阅者、事件抛异常、30 秒无响应、拿不到 UI 线程、用户取消或清空对话 —— 一律**拒绝执行**并说明原因，
  绝不静默执行。用户把设置里的开关关掉时才完全跳过确认。
- 兜底仍在：AI 的动作走**同一套舒适档与安全限速**（不绕过限速），急停在侧栏/悬浮窗/校准窗都只有一键。
